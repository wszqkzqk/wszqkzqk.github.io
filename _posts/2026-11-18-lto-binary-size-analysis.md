## 体积变化的反常现象

在构建系统里开启链接时优化 LTO，通常被默认为同时带来性能提升和体积缩减的手段。不久前 PvZ-Portable 调整 CI 构建参数时，给所有平台加上 LTO：Linux、Arch Linux、MSYS2、macOS、iOS 和 Android 使用 `-flto`，Windows MSVC 使用 `/GL` 与 `/LTCG`，WebAssembly 使用 `-Os -flto`。构建全部成功，产物体积的变化却相当分裂。

Linux 平台的静态构建和 Arch Linux 构建的体积都减少了两成左右；同样使用 GCC 的 MSYS2 只减了 5%；Android 的 APK 增加了 3.4%，MSVC x64 的 exe 增加了 2.3%，MSVC x86 则几乎没有变化。从表面结果看，这些涨跌既不能用编译器种类解释，也不能简单归因于静态链接或动态链接。

为弄清原因，笔者对比了开启 LTO 前后的全部九个平台构建产物，从二进制的段布局一路检查到了 WebAssembly 的指令统计。最终发现这些现象来自多个独立过程的叠加，每个过程在特定工具链下的权重不同。

## 测量原始代码

下载包的大小不适合作为衡量二进制体积的依据。CI 产物大多经过 zip 压缩，Android 的 APK 本身也是 zip 封装，iOS 发布的是 IPA。压缩算法对代码、静态数据、对齐填充和符号表的压缩率各不相同，直接对比压缩包很容易掩盖真实变化。

因此，分析前需要解包并读取原始二进制的内部结构。对 Linux 和 Windows 的 ELF、PE 文件使用 `objdump -h` 读取 `.text` 和 `.rodata` 等段的大小，并用 `objdump -p` 检查导入表；对苹果平台的 Mach-O 文件使用 `size -m` 读取 `__TEXT`、`__LINKEDIT` 等段；对 WebAssembly，由于常规 binutils 无法直接读取段结构，编写了一段脚本按照 LEB128 编码格式解析 `.wasm` 文件中的 `Code`、`Function`、`Elem`、`Data` 等 section。APK 和 IPA 则先解压，取出其中的动态库和可执行文件。

下表列出了基线构建与开启 LTO 的构建之间的实测结果。代码段一栏的数据不包括只读数据、资源或符号表。

| 平台 | 优化参数（基线 -> LTO） | 文件大小（基线 -> LTO） | 变化率 | 代码段大小变化 |
|---|---|---|---|---|
| Linux static | GCC `-O3` -> `-O3 -flto` | 13.68 MB -> 11.23 MB | -17.9% | 10,924,210 -> 9,004,274 B（-1.92 MB） |
| Arch Linux | GCC `-O3` -> `-O3 -flto` | 4.16 MB -> 3.31 MB | -20.4% | 3,453,620 -> 2,733,234 B（-720 KB） |
| macOS 主程序 | AppleClang `-O3` -> `-O3 -flto` | 3.35 MB -> 2.53 MB | -24.6% | 约 -823 KB |
| MSYS2 UCRT64 | GCC `-O3` -> `-O3 -flto` | 15.42 MB -> 14.65 MB | -5.0% | 11,948,320 -> 11,223,072 B（-725 KB） |
| WebAssembly | 混合 `-O3` 与 `-O2` -> `-Os -flto` | 7.87 MB -> 7.35 MB | -6.6% | 7,129,978 -> 6,645,373 B（-485 KB） |
| iOS 主程序 | AppleClang `-O3` -> `-O3 -flto` | 6.78 MB -> 6.30 MB | -7.0% | 5,320,278 -> 5,339,449 B（+19 KB） |
| MSVC x64 | MSVC `/O2` -> `/O2 /GL` | 8.73 MB -> 8.93 MB | +2.3% | 6,174,892 -> 6,388,732 B（+214 KB） |
| MSVC x86 | MSVC `/O2` -> `/O2 /GL` | 7.57 MB -> 7.63 MB | +0.7% | 5,591,370 -> 5,640,314 B（+49 KB） |
| Android APK | NDK Clang `-O2` -> `-O2 -flto` | 13.44 MB -> 13.90 MB | +3.4% | 6,853,984 -> 7,423,888 B（+570 KB） |

## 代码体积的两个相反过程

LTO 打破了源文件之间的编译边界，它对体积的影响始终包含两个方向相反的过程。

一方面，全局可见性让编译器能够确认某些函数或静态数据在程序的任何地方都没有被使用，从而直接停止生成这部分代码。另一方面，同一个全局视图也会暴露更多的内联机会。为了消除函数调用的开销，编译器会把其他模块的函数体复制到调用处，或者针对常见的实参值克隆出专门的函数版本。循环展开、对齐填充同样属于以增加指令数量换取执行速度的做法。

最终代码段是增大还是减小，取决于这两个过程在具体代码库和工具链上的净差值。

### 目标文件粒度保留的冗余代码

在桌面 Linux 和 macOS 的默认构建中，GCC 与 Clang 不会启用 `-ffunction-sections` 和 `-fdata-sections`，链接器默认也不开启 `--gc-sections`。一个源文件编译出的目标文件里，所有函数连续放置在同一个 `.text` 段内。

链接器以目标文件为单位取舍代码：只要目标文件中的任意一个函数被其他模块引用，整个 `.text` 段就会进入最终的可执行文件。该源文件中其余完全没被调用过的函数，也会一并留存在产物里。

对于由上百个源文件组成、内部存在大量未被完全用到的框架类和工具函数的项目，这种冗余相当可观。LTO 在 IR 层面重新组合了所有函数，使编译器能够按函数粒度进行可达性分析。Arch Linux 构建开启 LTO 后，`.eh_frame_hdr` 段从 `0x9adc` 缩减到 `0x568c`。这个段为每个包含异常展开信息的函数保存一个条目，其体积缩减约 44%，说明近半数的函数被直接跳过，代码段因此净减约 720 KB。

### 工具链默认优化等级与内联膨胀

如果使用 LTO 的平台原本就不存在上述冗余，体积的变化就会由另一个过程主导，尤其是原先默认优化等级较低的时候。

CMake 对桌面 GCC 和 Clang 的 `Release` 配置默认使用 `-O3`。在 `-O3` 下，单个编译单元内部的内联和循环展开已经相当充分。即使进入 LTO 阶段，新增的跨模块内联数量也较为有限，代码消除带来的收益得以保留。

Android 和 MSVC 的情况不同。Android NDK 的工具链文件默认将 `Release` 的优化设为 `-O2`，CMake 对 MSVC 的 `Release` 默认使用 `/O2 /Ob2`。在 `-O2` 或 `/O2` 下，编译器跨模块内联的尺度原本比较保守。一旦在链接阶段引入全程序视图，跨模块导入机制会把大量位于内联阈值边缘的函数释放出来，函数体在多个调用点被反复复制。

同时，这两个平台原本的链接器就已经清理了未引用函数。Android NDK 默认开启 `-ffunction-sections` 和 `-Wl,--gc-sections`；MSVC 默认使用 `/Gy` 将每个函数放入独立的 COMDAT 段，并通过 `/OPT:REF` 在链接期丢弃未引用函数。它们无法从 LTO 中获得额外的死代码消除收益，剩下的只有内联造成的膨胀。Android 的 `.text` 段因此净增 8.3%，x64 平台的 MSVC 净增 3.5%。

同一份代码在 MSVC x86 下只增长了 0.9%。这是因为 32 位 x86 的通用寄存器较少，函数参数大多经栈传递，跨模块内联省去调用开销的收益不如 x64 显著，编译器进行的激进内联也相对更少。

## 依赖库的构建方式与体积基数

以上分析仅涉及应用自身代码，而最终产物里往往还包含第三方依赖。依赖库是否具备 LTO 所需的中间代码，以及它们在总产物中占据的比例，决定了体积变化呈现出的百分比。

### 相同绝对缩减量，不同百分比

Arch Linux 和 MSYS2 使用相同的 GCC `-O3 -flto` 参数，前者代码段缩减约 720 KB，后者缩减约 725 KB，绝对值几乎一致。但 Arch Linux 的整体体积减少了 20.4%，MSYS2 只减少了 5.0%。

原因在于两者的分发方式不同。Arch Linux 构建动态链接系统安装的 `libSDL3.so.0` 等共享库，产物本身只有游戏代码，基数约 4 MB。MSYS2 构建则静态链接了 SDL3、SDL3_mixer、libopenmpt 与 C++ 运行库，产物的 PE 导入表中没有任何依赖库 DLL，整个 exe 达 15.4 MB。这十多兆字节的静态依赖全部是 pacman 预编译的纯机器码，不包含 GCC 的 GIMPLE 中间代码，因此不参与链接期重写。减少的 725 KB 除以一个远大于 Arch Linux 的分母，百分比自然只有约 5%。

### MSYS2 上游为何拒绝默认开启 LTO

Arch Linux 官方仓库在构建软件包时，默认配置已经启用了 LTO，而 MSYS2 的 `makepkg_mingw.conf` 明确将默认选项设为 `!lto`，上游 `mingw-w64-sdl3/PKGBUILD` 也没有单独开启这一选项。

这一选择源于 MSYS2 作为 SDK 的分发定位。包含中间代码的静态库在跨编译器分发时存在严重问题。GCC 生成的 GIMPLE 字节码严格绑定编译器大版本，用 GCC 15 编译的静态库在被 GCC 16 链接时会直接报错，Clang 更是无法识别。如果仓库里的静态库带有中间代码，用户升级编译器后就会面临大面积的链接失败。

此外，`makepkg` 打包时会对静态库执行 `strip` 和 `ranlib`。对于只包含字节码的 LTO 对象，这些工具很容易移除 `.gnu.lto_*` 段，导致库文件损坏。MSYS2 曾为此增加补丁，在保留静态库的包中强制追加 `-ffat-lto-objects`，同时保留机器码和中间代码，但代价是所有静态库的文件体积直接翻倍。为了保证数千个软件包的开箱即用，上游放弃全局开启 LTO 是合理的。

Arch Linux 虽然使用 LTO 编译上游依赖，但生成的 `libSDL3.so.0` 已经在打包时完成链接。作为独立分发的共享库，它必须导出完整的 `SDL_*` 符号表，游戏在链接时已不可能按自身的调用范围删减其内部代码。macOS 发布包内捆绑的 21 个 Homebrew 动态库在开启 LTO 前后逐字节一致，也是相同的道理。

### 源码静态构建中的依赖裁剪

Linux static 是观察到依赖库明显瘦身的唯一平台。该构建在 CI 中拉取 SDL3、SDL3_mixer、libopenmpt、libpng 等库的源码，并在包含 `-flto` 的环境下统一编译成静态库。

这些依赖库带着中间代码进入最终链接阶段，编译器不仅能优化游戏代码，还能按实际调用关系裁剪依赖内部的功能，例如未使用的窗口系统后端、音频格式解码模块和图像处理代码。在游戏自身约 720 KB 的缩减量之外，依赖部分又减少了约 1.2 MB，整体代码段由此下降了 17.6%。

## 符号表造成的体积幻觉

文件大小的减少有时与指令数量无关。iOS 构建开启 LTO 后，Mach-O 主程序的体积从 6.78 MB 降至 6.30 MB，但 `__TEXT` 段实际上微增了 19 KB，说明代码消除和内联膨胀恰好相互抵消。

真正减少的部分位于 `__LINKEDIT` 段。该段保存着符号表和字符串表，其大小从 1.26 MB 降至 0.77 MB，净减 491 KB。iOS 的日常构建不对可执行文件执行完整的 `strip`，而 LTO 的全程序分析会把大量原本需要导出的全局符号转化为文件内部的局部符号，不再将其名称保留在符号表中。

文件整体缩水的约 475 KB 几乎全部来自符号表收缩，而非机器码缩减。类似地，Android 的 APK 默认不对其中的 `.so` 动态库压缩，并按 4 KB 页对齐存放，因此 APK 体积会直接跟随代码段同步变化。如果只看这些表面数字，很容易对编译选项的实际效果产生误判。

## WebAssembly 上的控制变量实验

在 WebAssembly 平台上，LTO 的引入伴随着优化等级改为 `-Os`，两个变量同时发生了变化。仅比较基线和最终产物，无法区分 485 KB 的代码缩减中，多少来自死代码消除，多少来自 `-Os` 对展开的抑制。为此，笔者在本地基于基线代码构建了一个中间组，只设置 `EMCC_CFLAGS=-flto`，保留原有的优化等级，并在与 CI 完全相同的 Emscripten SDK 7.0.0 下进行了三组对比。

### 构建链中的混编优化等级

基线构建中，不同依赖组件实际上并未使用相同的优化等级。游戏本体和 SDL3_mixer 通过 `emcmake` 配置为 `Release`，Emscripten 的 `Emscripten.cmake` 将编译器识别为 `Clang`，但没有覆盖 `CMAKE_C_FLAGS_RELEASE`，因此这部分代码使用 CMake 默认的 `-O3`。通过 `emmake` 编译的 libopenmpt 默认采用 `OPTIMIZE=default`，同样映射为 `-O3`。

Emscripten 官方提供的 ports 库则不同，包括 SDL3、vorbis、zlib 和 libpng 在内的系统库由 `embuilder` 构建，`tools/ports/__init__.py` 中将编译参数固定为 `-O2`。在 PR 中，`EMCC_CFLAGS=-Os -flto` 被追加到所有 `emcc` 命令的末尾，覆盖了此前的 `-O2` 和 `-O3`，使整个工具链统一使用 `-Os -flto`。

### Asyncify 插桩带来的体积敏感性

该项目在链接参数中启用了 `-sASYNCIFY`。浏览器的 WASM 与 JavaScript 共享主线程，如果 C++ 代码中包含传统的模态对话框死循环或 `SDL_Delay` 等待，整个页面都会被阻塞。Asyncify 允许保留这类同步写法，由 Binaryen 的 `wasm-opt` 在链接阶段对控制流进行改写。

当程序执行到挂起点时，转换后的代码会将当前调用链上各函数的局部变量和执行位置保存到专门的内存区域，然后逐层返回到 JavaScript 主线程；定时器或事件触发后，代码再沿着调用链逐层进入，恢复保存的局部变量并跳转到之前的中断位置。

这一特性免去了大规模重构异步状态机的成本，但会在涉及调用链的函数中插入大量的状态检查、局部变量读写和跳转指令。转换过程由 `wasm-opt` 完成，随后继续执行的优化步骤则会根据链接期传入的优化等级决定是否进一步内联或复制这些插桩代码，使得最终的 `Code` 段体积对 `-O` 级别非常敏感。

### 实验数据与归因

三组产物均不包含 `name` 段或调试信息自定义段，因此符号表完全不影响这次测量：

| 指标 | 基线（无 LTO，`-O3` 与 `-O2` 混编） | 仅 `-flto`（保持原优化等级） | `-Os -flto` |
|---|---|---|---|
| 总大小 | 7,870,471 B | 8,364,452 B（+6.3%） | 7,349,194 B（较第二组 -1,015,258 B） |
| `Code` 段 | 7,129,978 B | 7,659,823 B（+7.4%） | 6,645,373 B（较第二组 -1,014,450 B） |
| 函数数量 | 7,058 | 5,950（-15.7%） | 6,018 |
| 平均函数体积 | 1,010 B | 1,287 B（+27.4%） | 1,104 B（较第二组 -14.2%） |
| `Elem` 段 | 11,125 B | 9,333 B | 9,332 B |
| `Data` 段 | 715,243 B | 682,406 B | 681,448 B |

第二组数据直接展现了仅开启 LTO 的效果。函数数量减少了一千余个，`Data` 段缩减了约 33 KB。这部分收益源于 IR 层的可达性分析：`wasm-ld` 虽然默认执行 `--gc-sections`，但 C++ 虚函数表和函数指针在 WASM 中依靠 `Elem` 段建立索引，链接器必须保守保留表内的所有函数。LTO 通过去虚拟化识别出了真正未被调用的表项，从而将其剔除。

然而，`-O3` 下的跨模块内联使平均函数体积上涨了 27.4%。内联带来的代码增量完全抵消了一千多个死函数消除所节省的空间，`Code` 段净增 530 KB，`.wasm` 文件反而膨胀了 6.3%。

第三组切换到 `-Os` 后，消除的死函数和静态数据基本得以保留，但 `Code` 段相比第二组直接减少了 1.01 MB。`-Os` 在 LLVM 编译阶段抑制了高昂的循环展开，同时在 `wasm-opt` 阶段限制了 Asyncify 插桩代码的跨函数内联。第三组函数数量比第二组略多 68 个，也印证了部分小函数从展开状态恢复为普通函数调用。

因此，WASM 产物能比基线缩小 6.6%，其中 LTO 的贡献在于彻底剔除了间接调用表中保留的冗余函数和静态数据，而真正产生净体积缩减的决定因素是 `-Os` 对内联和展开的约束。

## 对构建配置的启示

LTO 对体积的作用总是同时包含可达性裁剪与内联膨胀，不存在脱离工具链环境的固定结论。裸机桌面构建常因目标文件粒度保留大量冗余代码而获益；移动端和 MSVC 由于链接器已经做了函数级回收，在 `-O2` 下开启全程序优化往往会让体积增加。未剥离符号表的平台则可能因为符号内部化而出现文件体积与代码段变化相背离的情况。依赖库是否从源码构建、是否携带中间代码，以及 WebAssembly 这类特殊后端自身的转换过程，同样左右着最终结果。

对于 PvZ-Portable 这样一个负载较低的 2D 游戏，实际上并没有亟待解决的体积或性能瓶颈。在构建系统现代化过程中提升编译参数，桌面端清理了数百 KB 的冗余代码，WebAssembly 端通过 `-Os` 抑制了控制流插桩带来的膨胀，移动端即便略增了几个百分点，也在可接受的范围之内。此时直接采用经过 CI 验证的标准配置即可，不需要再为追寻理论上的最优平衡点增加额外的构建复杂度。
